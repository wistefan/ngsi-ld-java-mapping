# Implementation Plan: Compact expanded sub-attribute names of relationship instances on read

## Overview
Orion-LD 1.9.0 returns the sub-attributes of each instance in a RELATIONSHIP_LIST (2+ instances) under expanded names such as `https://uri.etsi.org/ngsi-ld/name` and `https://uri.etsi.org/ngsi-ld/default-context/validFor`. `EntityVOMapper` looks sub-attributes up by their short name, so a `fromProperties = true` ref comes back with only its id. The fix adds a small key-compaction helper that strips the NGSI-LD core and default-context prefixes. `EntityVOMapper` applies it before it matches sub-attribute keys to setters and before it merges override properties. Already-compact input does not change.

Out of scope (possible follow-up): full JSON-LD compaction against the `@context` in use. Prefix stripping covers the reported Orion-LD case.

## Steps

### Step 1: Add the `NgsiLdKeyCompactor` helper with unit tests
Create `src/main/java/io/github/wistefan/mapping/NgsiLdKeyCompactor.java`, a final utility class with a private constructor and tab indentation, like `ReservedWordHandler`:

- Named constants: `DEFAULT_CONTEXT_PREFIX = "https://uri.etsi.org/ngsi-ld/default-context/"` and `CORE_CONTEXT_PREFIX = "https://uri.etsi.org/ngsi-ld/"`. Keep them in an ordered list, longest prefix first, so the default-context prefix is checked before the core prefix it starts with.
- `public static String compact(String key)`: strips the first matching prefix. Returns the key unchanged when no prefix matches or when the key is `null`. **When a prefix was stripped, it then applies the parser's unescape rule**, `ReservedWordHandler.canUnescapeDuringParsing(k) ? ReservedWordHandler.removeEscape(k) : k`. `EscapeCleaningParser.cleanName` already does this for compact wire keys, but it cannot see an expanded key, because the key does not start with `tmfEscaped-`. The rule puts the result in the state a parsed compact key already has: `https://uri.etsi.org/ngsi-ld/default-context/tmfEscaped-@referredType` becomes `@referredType`, while a VO-collision key such as `.../default-context/tmfEscaped-value` stays `tmfEscaped-value`, the same as the parser leaves it. Keys that were already compact are returned unchanged, without the rule applied a second time.
- `public static <V> Map<String, V> compactKeys(Map<String, V> map)`: returns a new `LinkedHashMap` with compacted keys and keeps the insertion order. **On a collision, the key that was already compact wins** (an expanded key never overwrites a compact one). `null` gives `null`. When no key needs compaction, return the input map unchanged, so the compacted path costs nothing.
- One-line Javadoc per public member. The class gets a short comment that names the Orion-LD quirk.

Tests: `src/test/java/io/github/wistefan/mapping/NgsiLdKeyCompactorTest.java`, structured like `ReservedWordHandlerTest`:
- `@ParameterizedTest` + `@MethodSource` for `compact`: core prefix, default-context prefix, an already-compact key, an escaped expanded key (`.../default-context/tmfEscaped-@referredType` -> `@referredType`), an escaped expanded VO-collision key (`.../default-context/tmfEscaped-value` -> `tmfEscaped-value`), an already-compact escaped key (`tmfEscaped-@referredType` stays as it is), an unrelated URI (`https://example.org/name` stays as it is), and `null`.
- `compactKeys`: keys get compacted, the compact key wins on a collision in both insertion orders (including `@referredType` vs. `.../default-context/tmfEscaped-@referredType`), and the order is kept.

Acceptance: `mvn clean verify` passes. Nothing else in `src/main` uses the helper yet.

### Step 2: Compact sub-attribute keys in `EntityVOMapper` and add the Orion-LD regression test
Wire the helper into `src/main/java/io/github/wistefan/mapping/EntityVOMapper.java`. **Scope: compaction runs only on the relationship sub-attribute path** (`relationshipFromProperties` and the override merge in `getObjectFromRelationship`). The shared helpers `unescapeReservedKeys`, `handleProperty`, `handlePropertyList`, `propertyListToTargetClass`, `fromProperty`, `fromRelationship` and `toUnmappedProperty` are not changed. They also serve top-level attributes and unmapped properties, and top-level value trees (user data that may contain `https://uri.etsi.org/ngsi-ld/...` keys) must keep being returned as they are today.

1. **`relationshipFromProperties`** (~L543): at the start, compute `Map<String, AdditionalPropertyVO> subAttributes = NgsiLdKeyCompactor.compactKeys(relationshipVO.getAdditionalProperties())` once. Use it in every lookup: the direct `field` lookup, the `ReservedWordHandler.escapeReservedWords(field)` lookup, the `legacyNames` loop, and both `getRelationshipMap(...)` calls in the `RELATIONSHIP`/`RELATIONSHIP_LIST` branches. Do not mutate `relationshipVO`. Because `compact` applies the parser's unescape rule, an expanded `@referredType` is found by the same `field` lookup as a parsed compact one.
2. **Nested values of these sub-attributes.** The sub-attribute values can carry expanded keys too (for example `validFor` whose value map uses expanded keys). Add one private static walker `compactValueKeys(Object)` next to `unescapeReservedKeys`: it recurses through Map/List trees and applies `NgsiLdKeyCompactor.compactKeys` at every map level (so the compact key wins inside a value map as well). Add a private helper that returns a copy of the resolved `AdditionalPropertyVO` with a compacted value: `PropertyVO` -> new `PropertyVO` with `compactValueKeys(value)`, `PropertyListVO` -> the same per item, anything else (for example `GeoPropertyVO`, GeoJSON has no expanded keys) as it is. In `relationshipFromProperties`, apply it only to the `attributeValue` that is passed to `handleProperty`/`handlePropertyList`. `unescapeReservedKeys` then runs on the compacted tree unchanged and strips the escape prefix that `compact` kept for VO-collision keys. One-line Javadoc on each new private method, matching the file's density.
3. **`getObjectFromRelationship`** (~L846): merge `NgsiLdKeyCompactor.compactKeys(additionalPropertyVOMap)` instead of the raw map. Expanded override keys then replace the fetched entity's compact attributes instead of landing next to them as unmapped properties. Only the top-level override keys are compacted. The merged entity goes through the normal `fromEntityVO` path, which stays unchanged (see the scope note above).
4. **`fromProperty` / `fromRelationship` stay unchanged.** They are only reached from `toUnmappedProperty` (unmapped properties, which are top-level) and from their own recursion, not from the relationship-instance path, so the Orion-LD case does not need them. Do not add inline `compact(entry.getKey())` calls there: `fromRelationship` collects with `Collectors.toMap(Map.Entry::getKey, Map.Entry::getValue)`, which throws `IllegalStateException` as soon as `name` and `https://uri.etsi.org/ngsi-ld/name` compact to the same key. If a follow-up does extend compaction to them, it has to call `NgsiLdKeyCompactor.compactKeys(...)` once on `getAdditionalProperties()` before streaming, so the "compact wins" rule stays in one place.
5. Leave the top-level entity attribute handling as it is. Top-level keys are compacted by both brokers.
